# Frontend authorization

Protected operations require authentication and an active, non-deleted account, including superusers. Use independent feature grants: view to read, create to create a new Draft or Published record, and for existing owned content, edit plus API ownership to edit/publish/change status and delete plus API ownership to delete. Container policies are specified below. Ownership alone grants nothing. Explicit individual denials override inherited grants. Only trusted active `is_superuser === true` bypasses feature grants and ownership; role names never do. Moderator role names do not grant moderation or Admin panel access. No default role grants are inferred from persona names.

Use `usePermissions` for controls and `canModify(feature, apiResource, action)` for resource actions. The hook requires a successful current-user query matching the session. Never authorize from local storage, display names, form owner fields, or caller-supplied owner IDs. `permissionUtils.ts` resolves grants, `resourceAuthorization.ts` checks ownership, and `mutationAuthorization.ts` applies final fresh-profile/target checks through the shared RTK base query. Client-only parent locators are stripped from requests.

Shared categories, forum-container creation/edit/deletion, folder renames/deletion, roles/permissions, existing-account administration, cross-owner moderation, exports, dashboard/statistics reads, settings/logs/backups and standalone file deletion are active-superuser-only. The folder API exposes no creator or trusted delete/cascade capability; visibility, `document.delete`, and `can_upload` cannot authorize ordinary folder deletion. Backend authorization must enforce container and cascade restrictions atomically. Ordinary document-file deletion still requires `document.delete` plus uploader ownership. Ordinary users can delete only empty forum topics until safe cascade authorization exists. Replies require create, explicit `can_post` and an explicitly unlocked topic. Document uploads and nested folder creation require create plus parent `can_upload`; root folder creation requires create.

Delegated `user.create` sends only ordinary fields, with no role, superuser, status, permissions or payment assignment. The server must choose a safe default account role; a required caller-selected `role_id` contract must be resolved server-side. Existing account administration requires superuser. Preserve self-profile changes through `/user/users/me`; password, photo, notifications, registration, signup and recovery use separate self-service policies.

Role grants come from `/me.permissions`, overlaid by non-null `/me.user_permissions` actions. Personal false denies, true allows, and null/omitted actions inherit. The member editor displays inherited/effective access and explicit Allow/Deny/Inherit states. Existing rows PATCH only changed booleans. New personal overrides and persisted reset-to-inherit are blocked in both the editor and final RTK guard: the known API requires four non-null booleans on create and has no documented reset contract. Partial/nullable creation and reset support must be established before enabling these workflows. Role-row creation remains available.

Missing permissions, required ownership/capability data, inactive/deleted accounts or unresolved/mismatched identity fail closed. Startup hydrates the current profile once before route permission checks; guards observe the resolved session and never treat background fetching as denial. Reads use the resolved profile and explicit feature/admin/shared endpoint policies; unknown reads and writes deny, even for superusers. Public auth endpoints and current-profile hydration have named exceptions. Shared reads allow eligible users to use online presence, self notification preferences, and global search. Final writes retain fresh profile/target checks. Check current authorization on rendering, opening, submitting and confirming; hiding controls is insufficient.

View and Create remain independent. A direct RTK create may pass Create when page navigation is blocked by missing View; the UI does not grant View implicitly. Home offers authorized module links when only TechnicoPro, directory, or documents are available. Dashboard and standalone Moderation remain unrouted. Search displays only feature-authorized result rows and their visible count; the backend must filter resources, snippets, metadata and totals before returning them.

Profile refresh on focus/reconnect and mutation invalidation remains in place, with no polling. Direct attachment requests use the existing file helpers outside RTK preflights; server-side asset authorization is required. Cached content, downloaded files and opened Blobs cannot be revoked solely through client controls.

Frontend checks are UX safeguards and cannot secure the backend. See [implementation notes, changed files, tests and backend checklist](docs/frontend-authorization.md).
